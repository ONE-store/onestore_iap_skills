# 원스토어 인앱결제 연동

안드로이드 개발자가 원스토어 인앱결제 SDK를 붙이고, 진단하고, 릴리즈 전에 확인하도록 돕는다.

> [!important] 답변은 사용자의 언어로 — 이 문서를 베끼지 말고 옮겨라
> 이 문서와 참고 파일, 아래 모든 예시·틀·표는 **한국어로 적혀 있지만, 답은 요청이 온 언어로 한다.**
> 영어로 물으면 표의 판정 어휘·채워 넣을 틀·"~해줘" 요청 문장까지 **전부 영어로 옮겨서** 낸다 —
> 구조만 유지한다. 코드 식별자·SDK 상수는 원문 그대로, 개발자센터 메뉴 이름은 한국어 표기를
> 병기한다(화면이 한국어다). **답을 내보내기 전에 첫 문장·표 머리글·끝의 요청 문장이 사용자의
> 언어인지 확인하고, 하나라도 아니면 옮기고 나서 낸다.**

## 할 수 있는 일

사용자가 "무엇을 할 수 있냐"고 묻거나 **아무 요청 없이 이 스킬만 호출하면**, 아래를 안내하고
곧바로 상태 진단을 돌린다. 사용자는 자연어로 물으면 되고 절차 이름을 알 필요가 없다.

| 이렇게 물으면 | 이렇게 한다 |
|---|---|
| "지금 어디까지 됐어?" | **상태 진단** — 무엇이 있고 무엇이 빠졌는지 표로 (파일은 고치지 않는다) |
| "원스토어 인앱결제 붙여줘" | 의존성 · 매니페스트 `<queries>` · 매니저 클래스 배치 |
| "코인 3종 넣어줘", "광고 제거 상품도 있어" | 배치한 코드의 TODO를 앱에 맞게 채우기 |
| **"테스트 화면 추가해줘"**, "샘플 화면 만들어줘", "잘 되는지 눌러보고 싶어" | **테스트 화면 배치** — 로그인·상품·구매·소비/승인을 눌러 확인하는 Compose 화면. **직접 만들지 않고 참고 파일 원본을 배치한다** |
| "responseCode 7이 떠", 로그·스택트레이스 | **오류 진단** — 원인 · 재현 조건 · 수정 코드 · 문서 |
| **"결제가 안 돼", "왜 안 되지"** — 증상만 있을 때 | **증상 진단** — 로그부터 확보해 어디서 멈췄는지 가른다. 코드로 알 수 없는 것은 묻는다 |
| "로그 어떻게 봐?" | **진행 로그 안내** — `adb logcat -s OneStoreIAP` (디버그 빌드에서 결제 흐름 전체가 찍힌다) |
| "빌드가 안 돼", 자바·JDK 오류 | **빌드 환경 확인** — `references/build-env.md` |
| "릴리즈 전에 점검해줘" | 출시 전 점검 목록 전체 (파일은 고치지 않는다) |

경계도 함께 알린다 — Gradle 동기화와 실제 결제 테스트는 사용자가 해야 하고, 전용 라이브러리 모듈
생성은 다루지 않는다.

### 연동을 끝내려면 사용자에게 받아야 하는 값

**세 가지뿐이고, 셋 다 개발자센터에서 나온다.** 무엇이 필요한지 모르는 채로 시작하는 사람이 많으므로
**먼저 알려주고, 없으면 어디서 얻는지까지 말한다.**

| 값 | 어디서 | 없으면 어떻게 되나 |
|---|---|---|
| **라이선스 공개키** | 개발자센터 → **공통정보 → 라이선스 관리** | 결제가 시작되지 않는다 |
| **상품 ID 목록** | 개발자센터 → **In-App 정보**에 등록한 `In-App ID` | 상품 목록이 빈 채로 뜬다 |
| **그중 무엇이 소비성인지** | 앱 기획 — 다시 살 수 있어야 하는 것인지 | **오류 없이 조용히 깨진다.** 반드시 묻는다 |

#### 값을 요청할 때는 채워 넣을 틀을 준다

**"무엇이 비었다"만 말하면 사용자는 어디서 무엇을 가져와야 하는지 모른다.** 아래 틀을 그대로 내보내
**복사해서 채운 뒤 붙여 넣게** 한다. 각 줄에 **어디서 얻는지와 값이 어떻게 생겼는지**를 함께 둔다.
(사용자가 한국어가 아니면 이 틀을 **그 언어로 옮겨서** 낸다 — 맨 위 언어 규칙.)

```text
공개키: (여기에 붙여 넣어 주세요)
        개발자센터 → 공통정보 → 라이선스 관리에서 '라이선스 키'를 통째로 복사하면 됩니다.
        MII로 시작하는 긴 문자열 하나입니다.

상품 ID: (여기에 적어 주세요 — 예: coin_100, coin_500, remove_ads)
        개발자센터 → In-App 정보에 등록한 'In-App ID'입니다.
        여러 개면 쉼표로 구분해 전부 적어주세요.

소비성 상품: (위 상품 중 해당하는 것만 — 예: coin_100, coin_500)
        다시 살 수 있어야 하는 것만 적습니다. 코인·아이템처럼 쓰면 없어지는 것입니다.
        광고 제거·프리미엄 해제처럼 한 번 사면 끝인 것은 넣지 마세요
        — 넣으면 이미 산 사용자가 또 살 수 있게 됩니다.
```

- **값 자리는 비워서 낸다.** 예시 값을 자리에 채워 두면 그대로 두고 답하는 사람이 생긴다
- **예시 상품 ID는 이름만 봐도 성격이 드러나는 것을 쓴다**(`coin_100`은 소비성, `remove_ads`는
  영구성). 그러면 예시가 소비성 구분까지 함께 설명한다
- **실제 값을 예시로 쓰지 않는다** — 그 프로젝트에서 알아낸 상품 ID나 공개키 조각을 틀에 박아 두면
  대화 밖으로 새어 나간다. 이미 알고 있는 값은 **"확인한 상품 ID 세 개는 그대로 쓰겠습니다"처럼
  말로만** 언급하고, 틀에는 비워 둔다

- **틀은 그대로 복사되게 둔다.** 설명을 문단으로 풀어 쓰면 사용자가 무엇을 적어야 하는지 다시 헤맨다
- 등록이 아직 안 됐으면 **먼저 개발자센터에서 등록해야 한다**고 말한다. 그것 없이는 상품 조회가
  빈 목록으로 온다
- 값을 받으면 **어디에 넣었는지 파일과 함께 알린다**

**값이 없어도 연동은 시작할 수 있다.** 의존성·매니페스트·코드 배치까지 하고 값 자리는 비워 둔 뒤,
위 틀을 주고 멈춘다. **값을 받으러 진행을 막지 않는다.**

### 다음이 내 일이면 할 말을 준다

**남은 일이 내가 할 일일 때, 사용자가 해야 하는 행동은 "그것을 해달라고 요청하는 것" 하나다.**
그런데 일을 설명하면 사용자는 **그 일을 자기가 해야 하는 줄 알고 막힌다.** 그래서 **할 일을 설명하지
말고 할 말을 준다** — 그대로 복사해 보낼 수 있는 요청 문장을, 인용이나 코드 블록으로 눈에 띄게.

```text
다음처럼 말씀해 주세요.

  MainActivity에 원스토어 결제 매니저 연결해줘

그러면 앱 시작·복귀·종료 시 결제 연결을 처리하도록 붙이겠습니다.

그 다음에는:

  원스토어 결제 테스트 화면 추가해줘

테스트 화면에서 상품 조회, 구매, 소비·승인을 직접 확인할 수 있습니다.
```

- **요청 문장과 그 결과를 짝으로 낸다** — 무엇을 말하면 무엇이 되는지가 한 눈에 보여야 고를 수 있다
- **남은 단계가 둘 이상이면 순서대로 다 낸다.** 지금 것만 주면 매 단계마다 다시 막힌다
- **문장은 짧고 그대로 통해야 한다.** 스킬을 부르는 말을 쓴다("원스토어 결제", "테스트 화면") —
  사용자가 문장을 다듬어야 하면 안 준 것과 같다
- 사용자 몫과 내 몫이 **섞여 있으면 갈라서 적는다** — "개발자센터에서 등록해 주세요"와 "이렇게
  말해 주세요"는 다른 행동이다. 한 덩어리로 적으면 어느 쪽이 자기 일인지 모른다
- **"~하는 일입니다" 로 맺지 않는다.** 그것은 설명이고, 사용자는 그 다음에 무엇을 해야 할지 여전히
  모른다. 커밋 메시지 추천으로 답을 맺는 것도 같다 — 연동이 안 끝났는데 커밋이 다음 걸음이 아니다

## 기본 규칙

1. **SDK API를 지어내지 않는다.** 클래스·메서드·상수·버전은 `references/sdk-context.md`에 있는 것만
   쓴다. 거기 없으면 확인이 필요하다고 말한다. 구글 플레이 결제와 이름이 비슷하지만 다르다 —
   플레이 결제 이름을 이 SDK에 대응시키지 않는다.
2. **코드는 기억으로 쓰지 않고 참고 파일에서 가져온다.** 아래 참고 파일 중 **`.kt.txt` 로 끝나는 것
   전부가 그 대상이다** — 매니저·공개키·라이선스·**테스트 화면**. 그대로 복사하고 `__PACKAGE__`
   자리만 치환한다. 사용자가 요청하면 그다음에 손본다.

   **결제와 관련된 화면이나 코드를 만들어 달라는 요청을 받으면, 먼저 그 원본이 참고 파일에 있는지
   본다.** 있으면 새로 쓰지 않는다 — 원본은 실제 SDK로 컴파일과 실기 결제까지 검증된 것이고, 새로
   쓰면 그 검증이 전부 날아간다. 없을 때만 새로 쓰고, 그때도 SDK API는 `sdk-context.md`에 있는
   것만 쓴다.
3. **대상은 근거로 정한다.** 근거가 없거나 후보가 여럿이면 추측하지 말고 묻는다.
4. **확답하거나 질문한다. 흐리지 않는다.** "아마", "보통", "~일 수 있다" 로 답을 회피하지 않는다.
   판정에 필요한 정보가 없으면 **그 정보를 구체적으로 묻는다.** 흐린 답은 사용자에게 아무 판단도
   주지 못하고, 확인했다는 착각만 남긴다.
5. **근거는 눌러서 열리는 링크로 적는다.** 표·목록·문장·요약 어디서든, 각 항목이 **그 자리에서 홀로
   읽혀 파일을 열 수 있어야** 한다. 사용자는 한 행·한 항목을 떼어서 쓴다.

   **보이는 글자는 `파일이름:줄`, 링크 대상은 `file://` + 절대경로**로 적는다. 마크다운 링크 형식이다.

   ```text
   좋음   [OneStorePurchaseManager.kt:82](file:///Users/me/work/app/src/main/kotlin/com/example/onestore/OneStorePurchaseManager.kt)
   나쁨   /Users/me/work/app/.../OneStorePurchaseManager.kt    스킴 없음 — URL 이 아니라 열리지 않는다
   나쁨   app/src/main/kotlin/.../OneStorePurchaseManager.kt   상대경로 — 열리지 않는다
   나쁨   file:///Users/.../OneStorePurchaseManager.kt:82      경로에 줄 번호 — 경로로 성립하지 않는다
   나쁨   (:130)     :94-107     줄 번호만 — 어느 파일인지 알 수 없다
   ```

   **`file://` 스킴과 절대경로를 모두 갖춰야 열린다**(실측). 상대경로도, 스킴 없는 절대경로도
   열리지 않는다. 작업 디렉토리를 알고 있으므로 거기서부터 이어 붙인다 — `file://` 뒤에 `/` 로
   시작하는 경로가 오므로 슬래시가 셋이 된다. 경로에 공백이 있으면 `%20` 으로 바꾼다.

   **링크 대상에 줄 번호를 붙이지 않는다.** 경로에 `:82` 가 들어가면 경로로 성립하지 않는다. 줄
   번호는 보이는 글자에만 둔다 — 사람이 읽고 찾아갈 수 있다.

   **보이는 글자에는 경로를 넣지 않는다.** 긴 경로는 읽는 데 방해가 된다. 경로는 링크 대상에만 둔다.

   **더 읽을 자료를 안내할 때는 공개 문서 URL만 가리킨다.** 아래 참고 파일들은 **내가 읽는 자료이고
   사용자의 문서가 아니다.** 사용자에게 "`sdk-context.md`를 보라"고 하지 않는다 — 같은 내용이 공개
   문서에 있으므로 그 URL을 준다. 근거는 **사용자 프로젝트의 파일**을 가리킨다.

   같은 파일이 계속 나오면 반복이 중복처럼 보여 줄이고 싶어진다. **그 판단을 하지 않는다.** 한 항목
   안에서 여러 줄을 가리키는 것은 괜찮지만, 각각을 따로 링크한다. **항목이 갈리면 각각 다 적는다.**

   **표나 목록을 낸 뒤 스스로 확인한다** — 근거 칸에 링크가 아닌 항목이 하나라도 있으면 고친다.
6. **끝에 다음 한 걸음을 준다.** 무엇을 했는지로 끝내지 않고 **"다음은 이것을 하세요"를 한 줄로**
   맺는다. 사용자는 결제 연동을 처음 하는 사람이고, 지금 어디쯤인지·다음이 무엇인지 모른다.

   - 다음 것이 **사용자 몫이면 그 자리에서 할 수 있을 만큼 구체적으로 적는다.** 이름만 대지 않는다 —
     메뉴는 경로로(개발자센터 → 공통정보 → 라이선스 관리), 명령은 프로젝트 값을 넣어 완성해서,
     경로는 옮길 위치까지. **"동기화하세요" · "`adb`로 실행하세요" · "`src/debug/`로 옮기세요"는
     지시가 아니라 이름이다** — 읽은 사람이 다시 찾아봐야 하면 덜 적은 것이다
   - 다음 것이 **내가 할 일이면, 사용자가 그대로 붙여 쓸 요청 문장을 준다.** 아래 「다음이 내 일이면
     할 말을 준다」가 형식의 원본이다
   - **값이 없어서 멈췄으면** 무엇을 주면 이어서 하는지 적는다
   - 더 할 것이 없으면 **없다고 말한다.** 억지로 만들지 않는다

   **"이제 뭐 해야 해?" · "뭐라고 말해야 해?" 를 듣는 것은 이 규칙이 지켜지지 않았다는 뜻이다.**
   물어보게 만들지 않는다.
7. **생성물 디렉토리는 읽지 않는다.** `build/`·`.gradle/`·`.idea/`·`captures/` 아래는 판정 근거로
   쓰지 않는다. **빌드하지 않은 프로젝트에는 아예 없고**, 있어도 사람이 고칠 자리가 아니다.
   병합된 매니페스트·`BuildConfig`처럼 생성되는 파일이 궁금해도 **원본 소스를 근거로 삼는다.**
8. **기존 파일을 덮어쓰지 않는다.** 무엇이 있는지 보여주고 묻는다.
9. **범위는 앱 모듈까지다.** 전용 라이브러리 모듈을 만들지 않는다 — `settings.gradle(.kts)`의 모듈
   목록(`include`)을 건드리다 실수하면 프로젝트가 아예 열리지 않는다. **저장소 목록에
   `mavenCentral()`을 추가하는 것은 예외로 한다** — 그것이 없으면 의존성을 받을 수 없고, 한 줄
   추가라 되돌리기도 쉽다.

## 먼저 할 것: 상태 진단 (doctor)

"붙여줘", "설정 됐나?", "뭐부터 하면 되지?", **"이제 뭐 해야 해?"** 처럼 범위가 열린 요청이거나,
요청 없이 스킬만 호출됐거나, 프로젝트 상태를 아직 모르면 **진단을 먼저** 한다. **연동을 진행하던
중이어도 마찬가지다** — 어디까지 됐는지를 읽어서 판정하고, 기억으로 답하지 않는다.

- `references/checks.md`의 **목록 A**를 따라 확인한다.
- **이 단계는 읽기만 한다. 어떤 파일도 고치지 않는다.**
- 판정은 **있음 / 없음 / 해당 없음 / 확인 필요** 넷으로만 적는다.
- 근거는 **눌러서 열리는 링크**로 적는다 — 형식은 **기본 규칙 5번이 원본이다.** 앞에서 같은 파일을
  언급했어도 **매번 다시 적고**, 표나 목록을 낸 뒤 **링크가 아닌 항목이 없는지 스스로 확인한다.**
- **진단은 전체 표를 낸다** — 되어 있는 것도 보여주는 것이 이 절차의 목적이다. (릴리즈 점검은 반대로
  손댈 것만 적는다.)
- 판정 어휘의 뜻과 표 모양은 `references/checks.md`의 목록 A 절이 원본이다. **근거 표기 형식은
  기본 규칙 5번이 원본이다** — 두 곳에 적지 않는다.
- **표 아래에 다음 한 걸음을 적는다**(기본 규칙 6번). 그것이 값을 받는 일이면 **「값을 요청할 때는
  채워 넣을 틀을 준다」의 틀을 내고**(빠진 값만 골라서), 내가 할 일이면 **「다음이 내 일이면 할 말을
  준다」의 요청 문장을 낸다.**
- 사용자가 이미 진행을 지시한 경우가 아니면 여기서 멈추고 선택을 받는다.

## 연동 단계

1~4단계는 **진단에서 빠졌다고 나온 것만** 한다. 5단계는 진단 항목이 아니라 **사용자가 동작 확인을
요청할 때만** 한다.

### 1. 의존성

`references/dependencies.md`를 따른다. 방식은 근거로 고른다.

- `gradle/libs.versions.toml`이 있으면 → Version Catalog 방식
- 없으면 앱 빌드 파일 확장자로 Kotlin DSL / Groovy DSL을 가른다

`sdk-licensing`은 **유료 앱일 때만** 넣는다(애매하면 묻는다).

끝나면 **아래 세 줄을 그대로 알린다.** 대신 해줄 수 없는 일이라 "동기화가 필요하다"로 끝내면 사용자가
다시 찾아봐야 한다.

- 빌드 파일을 고치면 안드로이드 스튜디오 상단에 **"Sync Now" 배너**가 뜬다 — 그것을 누른다
- 배너가 안 보이면 툴바의 **코끼리 아이콘**(Sync Project with Gradle Files)
- 터미널만 쓰면 `./gradlew --refresh-dependencies`

**동기화가 자바 오류로 깨지면** `references/build-env.md`로 넘어간다. 결제 코드 문제가 아니다.

### 2. 매니페스트

`references/manifest-queries.xml.txt`의 `<queries>`와 INTERNET 권한을 앱 모듈
`AndroidManifest.xml`에 넣는다. 이미 있는 것은 건너뛴다. **가장 자주 빠지는 항목이다.**

### 3. 매니저 클래스

대상을 이 순서로 정한다.

1. SDK 의존성이 선언된 `build.gradle(.kts)` → 그 모듈
2. 그 파일의 `namespace` 값 → 패키지 `<namespace>.onestore`
3. 그 모듈의 `src/main/kotlin` 또는 `src/main/java` → 소스 루트

**후보 모듈이 둘 이상이거나 `namespace`가 없으면 고르지 말고 묻는다.**

참고 파일을 복사해 `__PACKAGE__`를 2번에서 정한 패키지로 바꾸고 해당 디렉토리에 쓴다.
**`purchase-manager.kt.txt`와 `license-key.kt.txt`는 함께 배치한다** — 매니저가 후자를 쓴다.
`license-manager.kt.txt`는 유료 앱에만 넣고, 그때도 키 파일은 하나만 둔다.

#### 운영 코드 연결은 반드시 알린다 (붙이는 것은 묻는다)

**매니저는 배치만으로는 돌지 않는다.** 액티비티가 생명주기 셋을 불러야 하고, **그 전에 `Listener`
구현이 있어야 매니저를 만들 수 있다.**

| 시점 | 부를 것 | 빠뜨리면 |
|---|---|---|
| 생성 | `start()` | 아무것도 동작하지 않는다 |
| **`onResume`** | **`onResumed()`** | **백그라운드에서 돌아온 경우 미처리 구매가 회수되지 않아 3일 뒤 자동 환불** |
| 종료 | `release()` | 연결이 남는다 |

가운데가 가장 놓치기 쉽다. 구매는 됐는데 소비·승인을 못 한 상태(강제 종료·네트워크 끊김·후처리 실패)는
**앱을 새로 시작할 때만 정리되고, 백그라운드에서 돌아오는 경로는 `onResumed()` 없이는 안 잡힌다.**

> [!warning] 이것은 세 줄짜리 일이 아니다 — 그렇게 말하지 않는다
> 매니저 생성자가 `Listener`를 받으므로 **콜백 여섯을 구현해야 컴파일된다.** 그중
> `onPurchaseCompleted`는 **상품을 실제로 지급하는 자리**이고, 무엇을 지급하는지는 앱마다 다르므로
> **스킬이 대신 쓸 수 없다.** 표만 내고 "셋을 부르면 된다"로 끝내면 사용자는 3줄짜리 일로 알고
> 그대로 시켰다가 컴파일 오류를 만난다. **필요한 것 셋을 함께 알린다** — 리스너 구현 · 지급 로직 ·
> 생명주기 호출.

**배치 직후 이 표를 그대로 내고, 붙여 줄지 묻는다.** 사용자 코드를 고치는 일이라 임의로 하지 않는다.
다만 **"안 붙여도 된다"고 말하지 않는다** — 없으면 결제가 동작하지 않거나 환불된다. 붙이지
않기로 했으면 **릴리즈 점검에서 다시 걸린다는 것**을 알린다.

붙여 달라고 하면 **어느 액티비티인지 근거로 정하고**(진입 액티비티, 또는 결제 화면을 띄우는 액티비티),
후보가 여럿이면 묻는다. 리스너 골격은 넣어 주되 **지급 로직은 `TODO`로 남기고 무엇을 채워야 하는지
말한다** — 추측해서 채우면 엉뚱한 것을 지급한다. 고칠 내용을 보여주고 확인받은 뒤에 넣는다.

##### 확인이 목적이면 이 단계를 건너뛰고 테스트 화면으로 간다

**테스트 화면은 이 연결이 없어도 돈다** — 화면이 자기 매니저를 스스로 만들고 스스로 해제한다(5단계).
그래서 **"잘 되는지 보고 싶다"가 목적이면 순서를 이렇게 권한다.**

```text
매니저 배치 → 값 채우기 → 테스트 화면으로 동작 확인 → 그 다음에 운영 코드 연결
```

운영 코드 연결은 **지급 로직을 결정해야 하는 가장 무거운 단계**다. 그것을 확인보다 먼저 시키면,
결제가 도는지도 모르는 상태에서 앱 구조를 고치게 된다. **다만 순서를 바꿨다고 이 단계가 없어지는
것은 아니라는 것을 함께 말한다** — 릴리즈 점검이 다시 잡는다.

연결까지 끝났으면 **로그 보는 명령을 알린다**(아래 「진행 로그」). 이 시점부터 실제로 돌기 시작한다.

끝나면 채워야 할 TODO를 알리고 **「값을 요청할 때는 채워 넣을 틀을 준다」의 틀을 그대로 낸다** —
어느 파일 어느 줄이 비었는지만 말하고 끝내지 않는다. 채울 것은 공개키, 상품 ID, **소비성 상품 지정**,
그리고 **서버가 상품을 지급하는 구조라면** 지급 전 서버 검증이다. SDK 로그는 빌드 종류로 자동
판별하므로 채울 것이 없다.

**서버 영수증 검증을 무조건 요구하지 않는다.** 구매 서명은 공개키를 넘긴 것으로 **SDK가 이미
검증한다** — 앱단에서 할 수 있는 검증은 그것으로 끝이다. 서버 대 서버 검증은 앱이 할 수 없는 일이고,
**서버가 지급에 관여할 때만** 필요하다. 서버가 없는 앱에는 **해당 없음**으로 판정한다. 근거는
`sdk-context.md`의 "서버 검증이 필요한 경우" 절이다.

### 4. TODO 채우기

실제 값을 받으면 배치한 파일을 고친다. **구조는 유지한다** — 특히 연결 보장 함수와 소비/승인
분기다. 그것을 없애는 변경이면 왜 결제가 깨지는지 말하고 대안을 제시한다.

**관리형 상품 중 무엇이 소비성인지 반드시 묻는다.** `INAPP`이면 무조건 소비한다고 가정하지 않는다 —
잘못 고르면 오류 없이 조용히 깨진다. 이유는 `sdk-context.md`의 "관리형 상품이 곧 소비성 상품은
아니다" 절에 있다.

#### 공개키는 평문으로 적지 않는다

공개 문서가 **"공개 키라 할지라도 앱 코드 안에 일반 문자열로 넣는 것은 안전한 방법이 아닙니다"** 라고
명시한다. 키를 받으면 `OneStoreLicenseKey`의 `ENCODED`·`MASK`를 채운다 — **평문 키를 어디에도
문자열 그대로 적지 않는다.**

1. 마스크를 정한다. 키와 길이가 달라도 되고 반복 적용된다
2. 평문 키의 각 바이트를 마스크와 XOR해 `ENCODED`를, 쓴 마스크를 `MASK`에 바이트 배열로 적는다
3. **되돌려서 원본과 대조한다** — `ENCODED`를 같은 마스크로 XOR한 결과가 받은 키와 **문자 단위로
   같은지** 확인하고, 그 확인을 했다고 말한다

3번을 건너뛰면 안 된다. 값이 틀려도 **컴파일은 통과하고 결제만 조용히 실패**한다. 계산이 확실하지
않으면 값을 적지 말고, 개발자가 직접 채울 수 있게 방법만 알려준다.

키를 서버에서 내려주는 구조라면 그쪽이 더 안전하다 — `get()` 안을 그 호출로 바꾸라고 안내한다.
어느 쪽이든 **키 은닉이 앱 안의 검증을 안전하게 만들지는 못한다**는 것을 함께 말한다. 다만 **서버
검증을 여기서 요구하지 않는다** — 필요 여부는 `sdk-context.md`의 "결제 완결과 검증" 절 기준으로
갈린다.

#### 값을 다 채웠으면 남은 둘을 요청 문장으로 낸다

**여기가 사용자가 가장 자주 막히는 자리다.** 값을 다 줬으니 끝난 것처럼 보이는데 **아직 아무것도
동작하지 않는다** — 생명주기 연결과 확인 수단이 없다. 그래서 값을 채운 뒤에는 **무엇이 남았는지
설명하지 말고 「다음이 내 일이면 할 말을 준다」의 요청 문장 둘을 순서대로 낸다.**

1. 생명주기 연결 (없으면 결제가 아예 동작하지 않는다)
2. 테스트 화면 (없으면 동작하는지 확인할 방법이 없다)

**커밋을 다음 걸음으로 제시하지 않는다.** 아직 한 번도 돌려보지 않은 상태다.

### 5. 테스트 화면 (요청하면)

**"테스트 화면 추가해줘"·"샘플 화면 만들어줘"·"눌러서 확인해보고 싶다"** 처럼 **동작 확인 수단**을
요청하면 `references/test-screen.kt.txt`를 매니저와 **같은 패키지·같은 소스 루트**에
`OneStoreTestScreen.kt`로 배치한다. 같은 패키지이므로 매니저를 import 하지 않는다.

**화면을 직접 만들지 않는다.** 원본은 실제 SDK로 컴파일되고 실기 결제까지 확인된 것이고, 새로 쓰면
소비·승인 분기와 조회 타입 같은 것이 조용히 어긋난다. 원본이 요구에 안 맞으면 **배치한 뒤 손본다.**

배치하기 전에 셋을 확인하고, 어긋나면 배치하지 말고 알린다.

| 확인할 것 | 근거 | 어긋나면 |
|---|---|---|
| 매니저가 배치돼 있다 | `OneStorePurchaseManager.kt` 존재 | 3단계를 먼저 한다 |
| 공개키가 채워져 있다 | `OneStoreLicenseKey`의 `ENCODED`·`MASK` | 값을 받아 4단계를 먼저 한다 — 안 채우면 키 예외로 화면이 뜨자마자 실패한다 |
| 상품 ID가 채워져 있다 | 매니저의 `PRODUCT_IDS` | 안 채우면 화면이 빈 목록만 띄운다 |
| 프로젝트가 Compose다 | 앱 빌드 파일의 Compose 설정, `androidx.compose.material3` 의존성 | Compose 화면은 컴파일되지 않는다고 알리고 배치하지 않는다 |

**연결은 배치한 뒤 물어본다.** 화면을 어디에 띄울지는 앱 구조에 달렸고, 진입 화면을 바꾸는 것은
사용자가 원하지 않을 수 있다. 파일을 놓고 나서 **연결해 줄지 묻고, 해달라고 하면 한다.** 묻지 않고
연결하지도, 묻지 않고 넘어가지도 않는다.

연결 방법은 둘이고, **기존 화면을 지우지 않는 쪽을 먼저 제시한다.**

| 방법 | 무엇을 하나 | 대가 |
|---|---|---|
| **별도 액티비티** | 화면을 띄우는 액티비티를 만들고 매니페스트에 등록한다. **실행 명령을 완성해서 준다**(아래) | 파일·매니페스트가 늘지만 **진입 화면은 그대로다** |
| 진입 화면 교체 | 진입 액티비티의 `setContent`를 `OneStoreTestScreen(this)`로 바꾼다 | 한 줄이면 되지만 **앱의 첫 화면이 바뀐다.** 원래 코드를 되돌릴 방법을 함께 알린다 |

별도 액티비티로 했으면 **실행 명령을 그 프로젝트의 값으로 완성해서 준다.** 이름만 알려주면 실행할 수
없다 — `applicationId`와 액티비티 클래스명을 넣어 그대로 붙여 쓸 수 있게 한다.

```text
adb shell am start -n <applicationId>/<액티비티 전체 이름>
```

어느 쪽이든 **기존 코드를 지우기 전에 무엇을 바꾸는지 보여주고 확인받는다.** 진입 화면을 바꿨으면
릴리즈 전에 되돌려야 한다는 것도 알린다.

배치한 뒤 이것을 알린다.

- 이 화면은 매니저를 `autoProcessPurchases = false`로 만든다 — 소비·승인을 **직접 눌러 확인**하려고
  자동 후처리를 끈 것이다. **운영 코드에서는 기본값(자동 처리)을 쓴다.** 3일 안에 후처리하지 않으면
  자동 환불된다
- **지급 로직이 없다** — 확인용 화면이라 상품을 실제로 지급하지 않는다. 운영 코드에 넣는다
- **누르기 전에 테스트 ID를 등록하라고 알린다.** 개발자센터 → **In-App 정보 화면의 '결제 테스트'
  버튼** → 테스트 ID 관리에서 원스토어 로그인 계정을 등록한다. 그 계정의 구매는 과금 없이 돈다.
  **등록하지 않은 계정으로 상용 환경에서 구매를 누르면 실제로 과금된다**
  (`sdk-context.md`의 테스트 절)
- **릴리즈 전에 지우거나 `src/debug/` 소스셋으로 옮긴다** — 운영 코드가 아니다. 진입점에 연결하지
  않았어도 코드는 배포본에 남는다
- **로그를 보는 명령을 함께 준다**(아래 「진행 로그」) — 화면에 안 보이는 것(연결·회수·소비/승인
  분기)이 로그에는 남는다
- **이 화면은 매니저를 스스로 만든다** — 운영 코드의 생명주기 연결이 없어도 돈다. 반대로 **운영
  연결이 이미 있으면 매니저가 둘 동시에 산다.** 그러면 운영 쪽(자동 처리 켜짐)이 구매를 먼저
  소비·승인해 버려서 **이 화면의 버튼을 누를 대상이 사라진다.** 둘 다 있는 상태라면 그렇게 보일 수
  있다는 것을 미리 알리고, 확인하는 동안 운영 쪽 화면을 띄우지 않게 안내한다

#### 이 화면을 운영 화면으로 고쳐 주지 않는다

"이걸 실제 결제 화면으로 써 달라"는 요청은 **범위 밖이다.** 확인용으로 만든 화면이고, 운영 화면은 그
앱의 디자인·지급 로직·오류 처리에 맞춰 개발자가 만드는 것이다. 고쳐 달라고 하면 **하지 않고 그 이유를
말한다.**

개발자가 **직접 고쳐 쓰는 것은 자유다.** 다만 그때 **자동 후처리를 반드시 켜야 한다**는 것만 알린다 —
이 화면은 꺼진 상태로 돌기 때문에, 그대로 내보내면 후처리가 아예 돌지 않아 **3일 뒤 결제가 전부 자동
환불된다.** 릴리즈 점검 15번이 그것을 블로커로 잡는다.

## 진행 로그

배치되는 매니저는 **디버그 빌드에서 진행 상황을 `OneStoreIAP` 태그로 출력한다.** 라이선스 확인도
같은 태그를 쓰므로 한 줄로 다 본다.

```text
adb logcat -s OneStoreIAP
```

연결 · 상품 조회 결과 · 결제 요청과 결과 · **회수를 건너뛴 이유** · 소비/승인 분기 판단 · 후처리
성공이 순서대로 남는다. 그래서 **마지막으로 찍힌 줄이 어디까지 갔는지**를 말해 준다.

- **매니저를 배치했으면 이 명령을 알린다.** 명령은 그대로 붙여 쓸 수 있게 완성해서 준다
- 릴리즈 빌드에서는 **경고·오류만** 남는다. 진행 로그는 `debuggable` 플래그로 갈리므로 끄는 것을
  잊을 일이 없다
- **기본 로그에는 구매 토큰·서명·`originalJson`을 넣지 않는다** — 진단에 필요한 것은 상품 ID·상태·
  응답 코드이고, 이 셋은 없어도 어디서 멈췄는지 다 가려진다
- **디버깅에 토큰이 필요하면 찍어도 된다** — 디버그 전용 로그는 개발자 기기에만 남는다. 다만
  **`Log.w`·`Log.e`처럼 릴리즈에도 남는 자리에는 넣지 않는다.** 게이트가 걸린 자리인지 보고 답한다

## 오류 진단

**들어오는 말이 두 가지고, 시작점이 다르다.**

| 받은 것 | 어디서 시작하나 |
|---|---|
| 오류 코드·스택트레이스·로그 | 아래 절차 1번부터 |
| **"결제가 안 돼요" · "빌드가 안 돼요" 처럼 증상뿐** | **`references/diagnose.md`** — 무엇을 확보하고 무엇으로 가르는지가 거기 있다 |

**증상만 들고 코드를 읽기 시작하지 않는다.** 원인이 코드 밖(기기·계정·개발자센터)인 경우가 많아서,
읽어서는 나오지 않는 것을 계속 읽게 된다.

**직접 확인할 수 있는 것은 직접 한다** — 빌드를 돌려 실제 오류 문구를 얻고, 로그를 직접 받는다.
**실행할 수 없으면 명령과 재현 절차를 주고 결과를 받는다.** 어느 쪽이든 **추정을 답으로 내지
않는다** — 방법은 `references/diagnose.md`가 원본이다.

오류 코드·로그·스택트레이스가 있으면 이렇게 한다.

1. `references/sdk-context.md`의 응답 코드 표에서 코드를 찾는다(`RESULT_*`는 서비스 결과,
   `ERROR_*`는 SDK 내부 오류).
2. 프로젝트를 읽어 그 경로가 처리되는 자리를 찾고, **눌러서 열리는 링크로 가리킨다.** 일반론으로 답하지
   않는다 — 그 프로젝트의 어느 줄이 문제인지 짚어야 고칠 수 있다.
3. **원인 · 재현 조건 · 수정(코드 포함) · 참고 문서** 네 부분으로 답한다. **판정 근거가 된 로그 줄을
   인용한다.**

먼저 확인할 만한 흔한 원인:

- `RESULT_ITEM_ALREADY_OWNED`(7) → 관리형 상품을 소비하지 않았다. 다만 **그 상품이 소비성인지 먼저
  확인한다** — 영구성 상품·구독에서 이 코드가 나오는 것은 정상 동작이라 고칠 것이 없다.
- 연결 문제 → **결제창이 떴는지로 갈린다. 먼저 그것을 묻는다.**
  - 결제창이 **안 뜬다** → 연결 실패다. 매니페스트 `<queries>` 누락, 또는 연결 보장 없이 API를 직접
    호출한 것을 본다.
  - 결제창까지 **갔다** → 연결은 성공했다(`launchPurchaseFlow`까지 도달했다는 뜻이다). `<queries>`는
    원인이 아니므로 **배제하고 그 근거를 말한다.** 스토어 환경 불일치(`onestore:dev_option`)와 테스트
    ID 미등록을 본다.
- `RESULT_NEED_LOGIN`(10) / `RESULT_NEED_UPDATE`(11) → 메시지가 아니라 복구 흐름이 필요하다.
- `RESULT_ITEM_UNAVAILABLE`(4) → 상품 ID 또는 개발자센터의 판매 상태.

**빌드가 안 되는 것은 대개 결제 코드 문제가 아니다.** 자바 버전·경로 오류(`Unsupported class file
major version`, `JAVA_HOME is not set`, `requires Java …`)면 `references/build-env.md`를 따른다.
**먼저 "배치한 코드 문제가 아니다"라고 말해** 사용자가 매니저를 뒤지며 시간을 쓰지 않게 한다.
배치한 코드 때문에 나는 빌드 오류(키 파일 누락·의존성 모듈 불일치 등)는 `references/diagnose.md`에
표로 있다.

## 릴리즈 점검

`references/checks.md`의 **목록 B**를 따른다. 진단과 마찬가지로 읽기만 한다. 개발사 서버에 달린
항목은 **코드에 연결 지점이 있는지까지만** 확인하고 나머지는 프로젝트 밖이라고 말한다.

**손댈 것만 적는다.** 통과 항목은 나열하지 않고 개수만 밝힌다 — 목록이 길어지면 고쳐야 할 항목이
통과 줄 사이에 묻힌다. 순서는 블로커 → 블로커 아닌 것 → 확인 필요 → 통과 개수다. 자세한 형식은
`checks.md`의 목록 B 보고 형식 절에 있다.

**점검 대상은 운영 코드다.** 테스트 화면(`OneStoreTestScreen.kt`)은 확인용이라 **일부러 운영 규칙을
어긴다** — 그 안의 결제·소비·승인 구현은 점검하지 않는다. 그 파일에 대해서는 **배포본에 남았는지만**
보고, 처리 방법(삭제 · `src/debug/`로 이동 · 도달 경로 없음)을 함께 제시한다. 자세한 판정 기준은
`checks.md`의 목록 B 머리말과 14·15번에 있다.
