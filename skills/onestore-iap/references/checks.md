# 점검 항목

두 가지 목록이다. **둘 다 읽기만 한다** — 점검하면서 파일을 고치지 않는다.

## 목록 A. 연동 상태 진단 (doctor)

"지금 어디까지 됐고 다음에 무엇을 하나"에 답한다. 표로 보고하고 권장하는 다음 한 걸음을 적는다.

**판정은 아래 넷 중 하나로만 적는다.**

| 판정 | 언제 | 예 |
|---|---|---|
| **있음** | 코드에서 확인됐다 | `sdk-iap 21.04.00` 있음 |
| **없음** | 코드에서 확인했고 없다 | `<queries>` 없음 |
| **해당 없음** | 조건이 성립하지 않아 필요하지 않다 | 무료 앱이므로 `sdk-licensing` 해당 없음 |
| **확인 필요** | 코드 밖 정보가 있어야 판정된다. **무엇을 알려주면 되는지 질문을 함께 적는다** | 확인 필요 — 유료 앱입니까? |

위 예시 칸에는 근거를 적지 않았다 — **판정 어휘만 보여주는 표**다. 근거의 모양은 아래 「보고 형식」과
`SKILL.md` 기본 규칙 5번에만 있다. 여기에 또 적으면 형식이 갈라진다.

**"없어도 정상일 수 있다", "아마", "보통", "가능성이 있다" 같은 표현으로 흐리지 않는다.** 사용자는
확답을 받으러 온 것이고, 흐린 답은 아무 판단도 주지 못한다. 코드로 판정할 수 없으면 **모른다고 하지
말고 무엇을 알려주면 판정되는지 물어라.** 표 아래에 그 질문들을 모아 두고, 답을 받으면 판정을
확정해 다시 알린다.

### 보고 형식

근거는 **눌러서 열리는 링크**로 적는다 — 보이는 글자는 `파일이름:줄`, 링크 대상은
**`file://` + 절대경로**이고 줄 번호를 붙이지 않는다. 상대경로도, 스킴 없는 절대경로도 열리지
않는다. 규칙 전문은 `SKILL.md` 기본 규칙 5번이다. 표로 낼 때는 이 모양을 그대로 쓴다
(아래 `/Users/me/work` 자리에 실제 프로젝트 경로).

```text
| 항목 | 판정 | 근거 |
|---|---|---|
| 공개키 채움 | 없음 | [OneStoreLicenseKey.kt:NN](file:///Users/me/work/app/src/main/kotlin/com/example/onestore/OneStoreLicenseKey.kt) — ENCODED 가 빈 배열 |
| 상품 ID 채움 | 없음 | [OneStorePurchaseManager.kt:NN](file:///Users/me/work/app/src/main/kotlin/com/example/onestore/OneStorePurchaseManager.kt) — YOUR_PRODUCT_ID 그대로 |
| 생명주기 연결 | 없음 | [MainActivity.kt:NN](file:///Users/me/work/app/src/main/kotlin/com/example/MainActivity.kt) — onResume 에 onResumed() 호출 없음 |
```

`NN`과 `/Users/me/work` 자리는 **모양을 보여주는 것이다.** 줄 번호와 경로는 그 프로젝트의 파일을
직접 읽어서 채운다 — 이 표의 숫자를 베끼면 엉뚱한 줄을 근거로 내놓는다.

항목마다 판정 한 줄, 그다음 **확인 필요 항목을 모은 질문**, 마지막에 권장하는 다음 한 걸음이다.
배치할 코드가 아직 없어 판정이 성립하지 않는 항목은 **해당 없음**으로 묶어 한 줄로 적는다.
**이 목록으로는 아무것도 고치지 않는다.**

| # | 확인할 것 | 확인 방법 | 없으면 |
|---|---|---|---|
| 1 | `sdk-iap` 의존성 | `*/build.gradle*`과 `gradle/libs.versions.toml`에서 `com.onestorecorp.sdk:sdk-iap` 또는 `libs.onestore.iap` 검색 | 시작 전 단계 — 의존성부터 추가 |
| 2 | 의존성 버전 | 공개된 최신 버전과 비교 | 보고만 한다. 요청 없이 올리지 않는다 |
| 3 | `sdk-licensing` 의존성 | 같은 파일들 | **유료 앱 전용이다.** 유료 앱이면 필수, 무료 앱이면 **해당 없음**. 어느 쪽인지 모르면 "확인 필요 — 유료 앱입니까?"로 적고 물어라 |
| 4 | 앱 매니페스트의 `<queries>` | `*/src/main/AndroidManifest.xml`에서 `com.onestore.ipc.iap.IapService.ACTION` 검색 | **Android 11+에서 연결이 실패한다** — 최우선 수정 |
| 5 | INTERNET 권한 | `android.permission.INTERNET` 검색 | 결제 통신이 되지 않는다 |
| 6 | 매니저 클래스 배치 | 모듈 소스 루트에서 `purchase-manager.kt.txt`의 클래스와 **`OneStoreLicenseKey`** 를 함께 찾는다 | 아직 코드가 배치되지 않았다. 매니저만 있고 키 파일이 없으면 **컴파일이 깨진다** |
| 7 | 공개키 채움 | `OneStoreLicenseKey`의 `ENCODED`·`MASK`가 빈 배열인지 본다 | 비어 있으면 `get()`이 예외를 던진다 — 결제가 시작되지 않는다 |
| 8 | 상품 ID 채움 | `YOUR_PRODUCT_ID` 검색 | 플레이스홀더가 남아 있다 |
| 9 | 구매 후처리 | `consumeAsync`·`acknowledgeAsync` 검색 | 3일 뒤 자동 환불된다 |
| 10 | 소비성·영구성 분기 | 관리형 상품을 반사적으로 전부 소비하고 있지 않은지 확인 | 영구성 상품을 소비하면 사용자가 다시 구매할 수 있게 된다 |
| 11 | 미처리 구매 회수 | `queryPurchasesAsync` 검색 | 소비되지 않은 관리형 상품 때문에 재구매가 막힌다 |
| 12 | 연결 보장 | **연결이 필요한** `PurchaseClient` 호출이 연결 보장 함수를 거치는지 확인. `launchUpdateOrInstallFlow`와 `GaaSignInClient` 호출은 **거치지 않는 것이 맞다** — 위반으로 잡지 않는다 | 서비스 연결이 끊긴 뒤 호출이 간헐적으로 실패한다 |
| 13 | 로그인·업데이트 복구 | `RESULT_NEED_LOGIN`·`RESULT_NEED_UPDATE`(또는 `GaaSignInClient`·`launchUpdateOrInstallFlow`) 검색 | 사용자가 해결 방법 없이 일반 오류만 본다 |
| 14 | **생명주기 연결** | 액티비티에서 `start()`·`onResumed()`·`release()` 호출을 각각 찾는다 | **배치만으로는 아무것도 돌지 않는다.** 특히 `onResumed()`가 없으면 백그라운드 복귀 때 미처리 구매가 회수되지 않아 3일 뒤 자동 환불된다 |
| 15 | 개발 옵션 meta-data | `onestore:dev_option` 검색 | 릴리즈에서는 주석 처리하거나 삭제해야 한다 |

## 목록 B. 릴리즈 전 점검

배포 전에 확인한다. 전부 실제로 사고가 나는 항목이다.

**점검 대상은 운영 코드다.** 스킬이 배치한 `OneStoreTestScreen.kt`는 동작 확인용이고 **일부러 운영
규칙을 어긴다** — 자동 후처리를 끄고, 상품을 지급하지 않고, 소비·승인을 사람이 눌러서 한다. 그 파일 안의
결제·소비·승인 구현은 **점검하지 않는다.** 아래 항목을 그 파일에 적용하면 전부 오탐이고, 오탐이
섞이면 진짜 블로커가 묻힌다. 그 파일에 대해 볼 것은 **14번(배포본에 남았는지) 하나뿐이다.**

| # | 확인할 것 | 왜 문제가 되나 |
|---|---|---|
| 1 | 앱 모듈 `AndroidManifest.xml`에 `<queries>`가 있다 | 없으면 Android 11+에서 연결 실패, 증상이 매니페스트 문제로 보이지 않는다 |
| 2 | `onestore:dev_option` meta-data가 주석 처리·삭제됐다 | 스토어 테스트용 스위치라 배포본에 들어가면 안 된다 |
| 3 | **릴리즈에 남는 로그를 본다.** ① `Logger.setLogEnable`에 넘기는 값과 앱이 직접 찍는 결제 로그가 **빌드에 따라 갈리는지**(`debuggable` 플래그·`BuildConfig.DEBUG` 등) — 상수 `true`면 실패. ② **게이트가 없는 호출에 구매 자격증명이 실려 있지 않은지** — `Log.w`·`Log.e`는 게이트하지 않는 것이 보통이므로 여기에 `purchaseToken`·`signature`·`originalJson`·`PurchaseData` 자체(`toString()` 포함)가 넘어가는 곳을 찾는다 | 결제 로그가 배포본 logcat에 남는다. 상수로 두면 끄는 것을 잊는다. **판정 기준은 "무엇을 찍었나"가 아니라 "릴리즈에도 남나"다** — 디버그 전용 로그는 개발자 기기에만 남으므로 토큰이 찍혀 있어도 **해당 없음**이다. `originalJson` 안에 토큰이 들어 있어 통째로 찍으면 같은 것이다 |
| 4 | 공개키가 채워져 있고 **평문 문자열로 적혀 있지 않다** | 공개 문서가 평문 상수를 금한다. 평문은 APK 문자열 목록에 노출돼 바꿔치기 대상이 된다. 릴리즈 난독화(Proguard/R8)도 함께 본다 |
| 5 | 모든 구매 경로가 3일 안에 `consumeAsync` **또는** `acknowledgeAsync`로 끝난다 | 아니면 미지급으로 판단해 자동 환불된다 |
| 6 | 소비성 상품은 소비하고, 영구성 상품은 승인만 한다 | 영구성을 소비하면 재구매가 열리고, 소비성을 소비하지 않으면 재구매가 막힌다 |
| 7 | 미처리 구매 회수가 **세 지점에서 다 돈다** — 앱 시작 · 로그인 직후 · **포그라운드 복귀**(액티비티 `onResume` → `onResumed()`). 그리고 **파는 상품의 타입을 빠짐없이 조회한다**(`INAPP`·`SUBS`·`AUTO`) | 소비되지 않은 관리형 상품 때문에 사용자가 막힌다. 빠진 타입은 승인 유실을 복구할 곳이 없다. **`onResume` 연결이 없으면** 강제 종료·네트워크 오류로 남은 구매가 백그라운드 복귀 때 회수되지 않아 **3일 뒤 자동 환불**된다 |
| 8 | 중복 지급을 막는 장치가 있다 | 소비 요청은 실패할 수 있다. **소비 성공 응답을 받은 뒤에 지급하면 서버 없이도 막힌다**(공개 문서가 제시하는 방법이고 배치되는 매니저가 이미 그 구조다). 서버가 있으면 구매 토큰 사용 여부를 서버에서 확인하는 쪽이 더 강하다. **이미 승인된 구매는 회수가 돌 때마다 완료 콜백으로 다시 들어오므로**(앱 시작·로그인 직후·이미 보유 응답), 누적 지급 상품이면 토큰 기준 확인이 따로 필요하다 |
| 9 | `RESULT_USER_CANCELED`를 실패로 다루지 않는다 | 정상 취소에 오류 창을 띄우는 것은 흔한 불만이다 |
| 10 | `RESULT_NEED_LOGIN` → `GaaSignInClient`, `RESULT_NEED_UPDATE` → `launchUpdateOrInstallFlow` | 이 둘은 메시지가 아니라 복구 흐름이 필요하다. `launchLoginFlowAsync`는 deprecated |
| 11 | **서버가 지급에 관여하면** 영수증 검증이 개발사 서버에서 이뤄진다. 서버가 없으면 **해당 없음** | 조작된 클라이언트가 "샀다"고 말하는 것을 서버가 믿으면 무료 지급이 된다. 서버가 없는 앱은 검증을 요청할 곳이 없어 판정이 성립하지 않는다 |
| 12 | 개발자센터에 실제 상품 ID가 등록돼 있다 | 아니면 `RESULT_ITEM_UNAVAILABLE`. 안 됐으면 **개발자센터 → In-App 정보**에서 `In-App ID`로 등록하라고 알린다 — 코드의 ID와 **글자 그대로 같아야** 한다 |
| 13 | 대상 OS에서 샌드박스 테스트를 최소 한 번 했고, 테스트 ID가 등록돼 있다 | 배포 전 필수다. 미등록 ID로 상용테스트를 하면 실제 과금된다 |
| 14 | 테스트 화면이 배포본에 없다 (`OneStoreTestScreen.kt`) | 확인용 화면이라 운영 규칙을 어긴다. 도달 경로가 없어도 코드는 APK에 남는다 |
| 15 | 운영 코드에서 자동 후처리를 끄지 않았다 (`autoProcessPurchases = false`가 테스트 화면 밖에 없다) | 끈 채로 나가면 후처리가 아예 돌지 않아 3일 뒤 전부 자동 환불된다 |

판정 어휘는 목록 A와 같다. 11·12·13번은 코드에서 **연결 지점의 유무만 단정**할 수 있고, 서버가
실제로 검증하는지·개발자센터 등록 상태·테스트 수행 여부는 프로젝트 밖이다. 그 부분은 **질문으로
적는다** — 통과로 처리하지도, "아마 됐을 것"으로 흐리지도 않는다.

11번은 **먼저 물을 것이 서버의 유무**다. "확인 필요 — 상품 지급을 앱에서 합니까, 개발사 서버에서
합니까?"가 첫 질문이고, 서버에서 한다는 답이 오면 그다음에 "서버에서 영수증을 검증하고 있습니까?"를
묻는다. **순서를 뒤집으면 서버가 없는 앱에 없는 것을 요구하게 된다.**

14번은 처리 방법을 함께 제시한다. 위가 확실하고 아래로 갈수록 약하다.

1. **삭제** — 확인이 끝났으면 이것이 가장 확실하다
2. **`src/debug/` 소스셋으로 이동** — 릴리즈 빌드에 들어가지 않는다. 계속 쓰고 싶을 때 쓴다.
   **옮길 경로를 그대로 적어 준다** — `src/main`을 `src/debug`로 바꾸고 패키지 디렉토리는 유지한다.

   ```text
   app/src/main/kotlin/<패키지 경로>/OneStoreTestScreen.kt
   → app/src/debug/kotlin/<패키지 경로>/OneStoreTestScreen.kt
   ```

   패키지 선언은 그대로 두고 **디렉토리만 옮긴다.** 옮긴 뒤 릴리즈 빌드가 되는지 확인하게 한다 —
   운영 코드가 이 화면을 부르고 있으면 릴리즈에서만 컴파일이 깨진다
3. **도달 경로만 없애기** — 코드는 배포본에 남는다. **연결한 적이 없으면 이미 이 상태**이고,
   연결했다면 그것부터 되돌려야 한다(진입 화면을 바꿨거나 액티비티를 등록했을 수 있다).
   **약한 조치라는 것을 함께 알린다**

판정은 파일 존재로 한다. 파일이 있고 `src/debug/`가 아니면 **있음**이고, 도달 경로가 없어도 그
사실을 근거에 적는다 — "노출되지 않으니 통과"로 처리하지 않는다. 다만 **블로커는 아니다**(과금이나
지급이 깨지지 않는다). 15번은 블로커다.

### 보고 형식 — 통과한 것은 나열하지 않는다

**손댈 것이 있는 항목만 적는다.** 통과 항목은 **개수만** 밝힌다 — `나머지 9항목 통과` 한 줄이고,
**항목 이름도 근거도 붙이지 않는다.** 목록이 길어질수록 통과 줄이 화면을 채우고, 정작 고쳐야 할
항목이 그 사이에 묻힌다. 점검을 부른 이유는 **무엇을 고쳐야 하는지 알기 위해서**다.

무엇이 통과했는지 궁금해할 수는 있으니 **물으면 그때 낸다.** 먼저 내밀지 않는다.

순서는 이렇게 한다.

1. **블로커** — 출시를 막아야 하는 것. 각각 무엇을 어떻게 고치는지까지
